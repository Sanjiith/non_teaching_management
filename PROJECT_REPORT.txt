1. ABSTRACT
--------------------------------------------------------------------------------

The BIT Non-Teaching Staff Portal is a full-stack web application built for
Bannari Amman Institute of Technology (BIT Sathy) to digitally manage the
administrative workflows of non-teaching staff. The backend runs on Node.js with
Express and MongoDB via Mongoose, and the frontend is a React 18 application
bundled with Vite, styled using Tailwind CSS, and communicating with the server
through Axios. The system defines three user roles: Admin, HOD (Head of
Department), and Staff, each with a separate protected dashboard and set of
pages. Authentication is JWT-based; users log in with their employee ID or email
and password, the server verifies credentials using bcrypt, issues a signed JWT,
and the client stores it in localStorage. Every protected API route runs through
auth middleware and role-based authorization middleware, and a department-level
isolation guard prevents HODs and Staff from accessing data belonging to other
departments. The system covers department management, staff management, shift
configuration, daily scheduling, attendance tracking, leave management with
balance tracking, server-side payroll calculation, in-app notifications, and
role-scoped reporting — all backed by dedicated input validators, a database seed
script, a migration script, and a suite of seven test files.


--------------------------------------------------------------------------------
2. INTRODUCTION
--------------------------------------------------------------------------------

2.1 Problem Statement
---------------------
Educational institutions like BIT Sathy manage a large number of non-teaching
staff across multiple departments. Traditionally, tasks such as attendance
marking, leave applications, payroll computation, and shift scheduling were
handled manually using paper registers or isolated spreadsheets. This approach is
error-prone, time-consuming, and lacks a centralized view for management.

2.2 Motivation
--------------
The need for a unified digital system that gives administrators, department heads,
and staff a single platform to manage and track all HR-related operations led to
the development of this portal. The goal is to reduce manual effort, improve
transparency, and ensure accurate payroll calculation based on real attendance
data.

2.3 Objectives
--------------
- Provide role-based access for Admin, HOD, and Staff users.
- Digitize attendance marking, leave applications, and approvals.
- Automate salary calculation based on attendance records.
- Allow shift creation and daily schedule assignment for staff.
- Generate attendance, leave, and payroll reports per role scope.
- Send in-app notifications for key events like leave approvals.
- Ensure security through JWT authentication and role-based middleware.

4. SYSTEM ARCHITECTURE
--------------------------------------------------------------------------------

The application follows a standard three-tier client-server architecture:

  [Browser / React Client]
         |
         | HTTP Requests (Axios)
         v
  [Express.js REST API Server]
         |
         | Mongoose ODM
         v
  [MongoDB Database]

Client Layer:
  The React frontend uses React Router for navigation and AuthContext for global
  authentication state. Each user role has a dedicated layout wrapper
  (AdminLayout, HODLayout, StaffLayout) and protected routes enforced by the
  ProtectedRoute component. The client communicates with the backend exclusively
  through RESTful API calls using Axios.

Server Layer:
  The Express server organizes all logic into the following layers:
  - Routes: Define API endpoints and attach middleware chains.
  - Middleware: Handle authentication (JWT verification) and authorization
    (role checking and department isolation).
  - Validators: Validate and sanitize all incoming request data.
  - Controllers: Handle business logic and prepare responses.
  - Services: Contain pure business logic (payroll calculation, notifications)
    separated from controller code for testability.
  - Models: Define Mongoose schemas for all database collections.

Database Layer:
  MongoDB stores all application data in 8 collections:
  Users, Departments, Attendance, Leaves, Shifts, Schedules, Payroll,
  and Notifications.

5. USER ROLES AND ACCESS CONTROL
--------------------------------------------------------------------------------

5.1 Admin
---------
- Full system access across all departments.
- Can create, update, and deactivate departments.
- Can create, view, update, and delete staff accounts.
- Can create and manage shift templates.
- Can assign shifts to staff via daily schedule entries.
- Can mark and correct attendance for any staff.
- Can approve or reject leave requests from any department.
- Can generate and manage payroll records (Draft, Processed, Paid).
- Can view system-wide reports (attendance, leave, payroll, schedule).

5.2 HOD (Head of Department)
-----------------------------
- Scoped strictly to their own department.
- Can view attendance of department staff.
- Can mark or correct attendance for department staff.
- Can approve or reject leave requests from their department.
- Can assign and update shift schedules for their department staff.
- Can view payroll records of staff within their department.
- Can view department-scoped reports (attendance, leave, schedule).

5.3 Staff (Non-Teaching Staff)
-------------------------------
- Can view their own attendance history and statistics.
- Can apply for leave specifying type, date range, time, and reason.
- Can view and cancel their own leave applications.
- Can view their own assigned daily schedule.
- Can view their own payroll slips.
- Can view their own personal reports (attendance, leave, payroll).
- Can update their own profile information.

Access is enforced on the server through:
  - auth.middleware.js  : Verifies the JWT token on every protected route.
  - role.middleware.js  : Checks role permissions (authorize function).
  - departmentAccessGuard: Blocks HOD/Staff from accessing other departments.
  - userAccessGuard     : Blocks Staff from accessing other users' data.

6. IMPLEMENTED MODULES
--------------------------------------------------------------------------------

6.1 Authentication Module
--------------------------
- Login using Employee ID (or email) and password.
- Server verifies credentials with bcrypt.compare().
- Issues a signed JWT token (expires in 7 days).
- Client stores token in localStorage and restores session on reload.
- /api/auth/me returns the currently authenticated user.
- Logout endpoint clears the session on the client side.

6.2 Department Management
--------------------------
- Admin can create departments with a unique name, unique code, and assigned HOD.
- Admin can update or delete departments.
- All authenticated users can list departments.
- HOD and Staff are restricted to viewing only their own department.

6.3 Staff (User) Management
-----------------------------
- Admin can create staff accounts with: name, employee ID, designation, phone,
  joining date, basic salary, department, role, and profile image.
- Admin can update or delete any staff account.
- HOD can view staff within their department.
- Staff can view and update their own profile.
- Accounts have an isActive flag; inactive accounts cannot log in.

6.4 Shift Management
---------------------
- Admin creates shift templates with a name, start time, end time, working hours,
  optional department scope, and active status.
- Shifts are available to be assigned to staff via the schedule module.
- Admin can update or delete shift templates.
- All authenticated users can view available shifts.

6.5 Schedule Management
------------------------
- Admin and HOD can assign a shift to a specific staff member on a specific date.
- Each schedule entry links a staff member, department, shift, and date with
  start/end times and a status (Scheduled, Completed, Cancelled, On Leave,
  Conflict).
- A unique constraint prevents assigning more than one shift per staff per day.
- Staff can view their own upcoming schedule.
- HOD/Admin can view all schedules for their department.
- A notification is sent to the staff member when a schedule is assigned.
- Admin and HOD can update or delete schedule entries.

6.6 Attendance Management
--------------------------
- Admin and HOD can mark or correct attendance for staff.
- Each attendance record stores: user, date, status, optional check-in time,
  optional check-out time, shift reference, and remarks.
- Status values: Present, Absent, Leave, Holiday, Weekly Off.
- A unique constraint prevents duplicate attendance records per user per day.
- Staff can view their own attendance history.
- Attendance data is used directly in payroll calculation.

6.7 Leave Management
---------------------
- Staff can submit leave applications with:
    Type    : Casual Leave, Medical Leave, Earned Leave, Maternity Leave,
              Paternity Leave, or Other.
    Dates   : From date, to date (totalDays auto-calculated).
    Time    : Optional start and end time (supports half-day = 0.5 days).
    Reason  : Free-text reason field.
- Leave balances are tracked per staff with 12 days allocated each for
  Casual, Medical, and Earned leave per year.
- On application submission: days are reserved from the balance.
- On approval: reserved days are marked as used.
- On rejection or cancellation: reserved days are released back.
- Overlap detection prevents a staff from submitting overlapping date ranges.
- HOD and Admin can approve or reject leave applications.
- Staff can cancel their own pending leave applications.
- Notifications are triggered on submit, approve, reject, and cancel events.

6.8 Payroll Management
-----------------------
- Payroll is generated server-side only by the Admin.
- Payroll preview (dry run) available before saving.
- Calculation formula:
    applicableSalary  = min(basicSalary, 40000)
    totalWorkingDays  = calendar days in month (excluding Sundays + holidays)
    dailySalary       = applicableSalary / totalWorkingDays
    absenceDeduction  = unauthorizedAbsentDays * dailySalary
    grossSalary       = applicableSalary + totalAllowances
    netSalary         = grossSalary - absenceDeduction - totalDeductions
- Approved leave days do NOT cause deductions.
- Weekly offs and holidays are NOT counted as working days.
- Allowance fields: HRA, DA, TA, Medical, Other (default zero).
- Deduction fields: PF, PT, TDS, Loan Repayment, Other (default zero).
- Payroll status lifecycle: Draft → Processed → Paid.
- Unique constraint prevents duplicate payroll per user per month per year.
- HOD can view payroll records for their department staff.
- Staff can view their own payroll slips.

6.9 Notification System
------------------------
- In-app notifications are stored in the database linked to individual users.
- Notification types: info, success, warning, error.
- Notifications have a title, message, type, read status, and optional link.
- Triggered automatically by: leave apply, leave approve, leave reject,
  leave cancel, and schedule assignment.
- Users can fetch their own unread notifications.

6.10 Reports Module
--------------------
Admin Reports:
  - /api/reports/admin/attendance : Attendance summary (all staff, filterable by
    month, year, department). Includes per-department breakdown.
  - /api/reports/admin/leave      : Leave summary across all staff.
  - /api/reports/admin/payroll    : Payroll overview for all staff.
  - /api/reports/admin/schedule   : Schedule report across all departments.

HOD Reports (department-scoped):
  - /api/reports/hod/attendance   : Attendance for HOD's department.
  - /api/reports/hod/leave        : Leave summary for HOD's department.
  - /api/reports/hod/schedule     : Schedule report for HOD's department.

Staff Personal Reports:
  - /api/reports/my/attendance    : Own attendance summary.
  - /api/reports/my/leave         : Own leave history and balances.
  - /api/reports/my/payroll       : Own payroll history.

11. SECURITY CONSIDERATIONS
--------------------------------------------------------------------------------

- Passwords are hashed using bcryptjs with a salt round of 12 before storage.
- JWT tokens expire after 7 days and must be sent in the Authorization header.
- The password field is excluded from all database query results by default.
- Role-based middleware (authorize) blocks unauthorized role access on every
  protected route.
- Department isolation guard ensures HODs and Staff cannot access or modify
  data outside their own department.
- User access guard prevents Staff from viewing or modifying other users' data.
- Input on all API routes is validated and sanitized through express-validator
  before reaching the controller layer.
- CORS is configured to accept requests only from the known client origin.

for non-teaching staff at Bannari Amman Institute of Technology. The system
provides a secure, role-scoped, and centralized platform that eliminates manual
record-keeping for attendance, leave, shifts, schedules, and payroll. The
modular MERN stack architecture ensures that each feature area is independently
maintained, validated, tested, and extensible.

Key achievements:
- Three-role access control system with department-level data isolation.
- Real-time leave balance tracking with reservation and release logic.
- Automated server-side payroll calculation with a ₹40,000 salary cap.
- In-app notification system for key HR events.
- Comprehensive reports for each user role.
- Input validation on all API routes.
- Full test coverage across authentication, attendance, leave, schedule,
  and payroll modules.

Future Enhancements:
- Email/SMS notifications in addition to in-app notifications.
- PDF generation for payslips.
